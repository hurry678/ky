## 这个仓库真正有用的地方

不是结论，是**方法与错误记录**。方向一死于连续被占，方向二正在被逐格挤压。两个目录的 README 都把"我错在哪"单列一节。

### 检索纪律（方向一死于违反这三条）

1. **不要只查 arXiv。** 方向一两次撞车分别是数据库会议论文（VLDB 2025）与向量数据库论文；方向二漏掉 ICLR 2025 的 Composable Interventions，是 Google Scholar 才查到的。
2. **不要沿单轴列关键词，要枚举交叉带。** 竞品坐在交叉格上：「属性/对象 × 机制或控制权归属 × 数据类型 × 应用场景」。按「agent memory」检索永远找不到向量数据库那篇。
3. **不要采信任何二手转述。** 方向一两次误判都源于此：一次因采信"场景不同"没读原文，一次因误读一行列表摘要就虚报撞车。看到相关标题就把摘要拉出来自己读。

**渠道**（均已实测可用）：arXiv API、**Google Scholar**、Semantic Scholar 引文图、DataCite、IETF datatracker。
**实测不可用**：CNKI/万方学位论文库（Scholar 零索引，需机构凭据）。

### 一个更结构性的教训

"把一个已知原语应用到 LLM/Agent 上"这个动作已经饱和——格子按月被填。方向一（密码 × 删除）、候选 A（密码 × agent 权限，被 CAPMAS 等 8 篇占）、方向二的各格，都是这么被挤掉的。

**扛得住的是两类**：需要真下功夫才拿得到的实测现象（门槛是工作量），以及评测方法学/复现性研究（供给不足且难被抢）。

**以及一条结构原则**：不要把承重放在被密集圈地的那一半。方向一把密码机制当承重，一篇论文压塌；方向二把承重放在"绑定"（六条路径验证无占据者），评估那半的格子被填也不影响论文成立。

### 对"被占"的正确态度

**对不要求发表的学位论文，被占不等于死，被占等于你有了基线。** 方向一真正的死因不是被占，是**承重的那一半被占且只剩一个点**。方向二的量化/剪枝/蒸馏格全被占，但它们变成有代码可跑的对比基线，反而让实验设计更明确。
